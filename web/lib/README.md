# Pulse extended libraries (`web/lib/`)

Pure JavaScript cores for the Pulse features that go beyond the local log: live recording, Bluetooth sensors, segments, privacy zones, routing, medical records, ECG, clinician export, the AI coach and calendar export.

Each file is a plain script that defines exactly one frozen global object (`var PulseX = (function () { ... })();`). No DOM, no network, no storage, no timers, no `Date.now()`, no randomness, no `eval`. The app inlines them into its single HTML file. Anything that needs the network (Overpass, a model host) is fetched by the app through its gate, and the result is passed in. Callers pass the current time where one is needed.

Run the tests (Node 18 or later, no dependencies):

```
node web/lib/test/run.mjs          # all
node web/lib/test/run.mjs ecg      # files whose name contains "ecg"
```

Each module is loaded into an empty `node:vm` context, the same way it runs inlined in the page. `purity.test.mjs` checks that every module defines only its global, is frozen, and does not mention DOM, network, storage, timer or dynamic-code APIs.

Errors are thrown as `Error` objects with a short `code` (for example `short`, `size`, `json`, `input`) and a plain message the app can show.

### Input conventions

- Bytes: a `DataView` (what Web Bluetooth delivers), `ArrayBuffer`, any typed array, or an array of 0 to 255. Capped at 512 bytes (the ATT maximum).
- GPS fixes for `record.js`: `{t, lat, lon, acc, alt}` with `t` in milliseconds (the Geolocation API unit). Tracks for `segments.js` and `privacy.js`: `{lat, lon, t}` with `t` in seconds.
- Daily metrics for `report.js` and `coach.js`: `{date, rhr, rmssd, sdnn, sleep, weight, sys, dia, load}`. `date` is `"YYYY-MM-DD"` or the core's day number (days since 1970-01-01). Units: bpm, ms, hours, kg, mmHg.

## Method and limits

**Heart rate (0x2A37).** Flags bit 0 selects uint8 or uint16 bpm; bits 1 and 2 are sensor contact (0 or 1 not supported, 2 supported without contact, 3 contact); bit 3 adds a uint16 energy expended in kJ; bit 4 adds one or more uint16 RR intervals in units of 1/1024 s. Little endian. Truncated fields throw; an odd trailing RR byte and reserved flag bits produce warnings. Live RMSSD: RR outside 300 to 2000 ms is rejected, as is any beat more than 20 percent from the median of the last 5 accepted beats. Successive differences are only taken between adjacent accepted beats, never across a rejected one. Five consistent "rejected" beats in a row reseed the reference, so a real change in rhythm (or a bad first beat) is not rejected forever. The rolling window holds about 60 s of beats (300 at most) and reports nothing below 10 pairs. RMSSD from a strap is a short-window value; it is not comparable to a morning reading from another device.

**Blood pressure (0x2A35).** Flags: bit 0 kPa (else mmHg), bit 1 time stamp (Date Time, 7 bytes), bit 2 pulse rate (SFLOAT), bit 3 user id (uint8, 255 unknown), bit 4 measurement status (16 bits: body movement, cuff too loose, irregular pulse, 2-bit pulse rate range, improper position). Systolic, diastolic and mean arterial pressure are SFLOAT. SFLOAT is a 4-bit signed base-10 exponent over a 12-bit signed mantissa; 0x07FF NaN, 0x0800 NRes, 0x07FE +infinity, 0x0802 -infinity and 0x0801 reserved are reported as specials with no value. kPa values are also given in mmHg (x 7.500615758). The cuff's time stamp has no time zone and is passed through as local wall-clock time.

**Recording.** Fixes with accuracy worse than 30 m, bad coordinates or non-increasing time are dropped. A fix that implies a speed above the sport limit (run 12, walk and hike 6, ride and other 30 m/s, plus the stated accuracy of both fixes) is a spike; four self-consistent spikes in a row re-anchor the track instead. Positions are smoothed with a 3-fix moving average, and distance is the haversine (R = 6,371,008.8 m) between smoothed positions, added only once the smoothed position has moved at least 3 m from the last counted point, so standing jitter adds nothing. Auto-pause uses the net smoothed displacement over 5 s: below 0.6 m/s for 5 s pauses, above 1.2 m/s for 3 s resumes (hysteresis band). The dwell before a pause is taken off moving time; the confirmation time before a resume is credited back with its distance. Splits are interpolated to the exact split distance. Current pace covers the last 400 m of moving time. Above `maxPoints` (200,000) the stored track is decimated by 2; totals are unaffected. Tested limits: within 3 percent of true distance on a straight synthetic track with 2.5 m noise; curved real tracks will run slightly short because of smoothing.

**Segments.** A segment is the track between two indices, resampled every 10 m, with a start gate and end gate (lines 2 x 25 m wide, perpendicular to the track direction averaged over the first or last 30 m) and a 30 m corridor. An effort starts where the track crosses the start gate in the segment direction and ends at the next end-gate crossing; both crossing times are linearly interpolated between fixes. It is accepted only if every track point between the crossings is within the corridor of the segment line, every segment checkpoint is reached in order by the track (this is what rejects shortcuts, including ones that stay inside a wide corridor), and the effort length is 0.9 to 2.5 times the segment length. Crossing the start gate again before the end hands the effort to the later crossing. Loop segments (same start and end gate) work. Geometry uses a local tangent plane around the segment start, accurate for segments of a few km.

**Privacy zones.** Default: 200 m around each saved place, plus the first and last 200 m of each activity. The ends are cut both along the track and as a circle around the actual start and end point, so a route that passes home again later is cut there too. A 5 m margin is added by default. Invalid points are dropped; an invalid zone throws instead of being skipped, because skipping it would leak the place it protects. Only `lat`, `lon`, `t`, `ele` and `hr` are copied out. The result is split into runs so the app never draws a line across a removed zone. `violations()` is the independent re-check the hub runs. Randomized tests assert that no surviving point lies inside any zone.

**Routing.** Graph from Overpass `[out:json]` ways with a `highway` tag. Foot allows footway, path, pedestrian, steps, track, living_street, residential, service, unclassified, road, cycleway, bridleway and tertiary to primary; bike allows cycleway, residential, living_street, unclassified, service, track, path, road and tertiary to primary, plus footway, pedestrian and bridleway only with `bicycle=yes|designated|permissive`. Motorways and trunks are never used. `access=no|private` excludes unless the mode tag allows it; `foot=no` and `bicycle=no` exclude; `bicycle=dismount` costs at least 3x. For bikes `oneway=yes|true|1|-1|reverse` and `junction=roundabout` are honored, and `oneway:bicycle=no` or `cycleway=opposite*` make the way two-way; pedestrians ignore `oneway` unless `oneway:foot` is set. Edge cost is length x a highway factor (1.0 preferred to 2.0 primary roads; bikes x1.3 on unpaved surfaces) x (1 - w x heat) with w up to 0.8 and heat in 0 to 1. A* uses straight-line distance x the cheapest factor x (1 - w), which is admissible, and is checked against Dijkstra on random grids. Loops: triangles start, A, B at 8 headings with sides of target / 3 / 1.25, legs that reuse earlier edges cost 4x, scored by length error, reuse, unpaved share (bike) and heat; only loops within 25 percent of the target are returned. GPX is 1.1 with escaped names and 7-decimal coordinates. Elevation is not modeled here. The fixture `test/fixtures/overpass_small.json` is a hand-laid synthetic grid, not real map data.

**FHIR.** Accepts a Bundle (including nested Bundles), a single resource (Apple Health `clinical-records/*.json` files hold one resource each), an array, or several files with `parseMany`. Input must be plain JSON: strings must start with `{` or `[`; parsed objects may contain only null, booleans, finite numbers, strings, arrays and plain objects (no functions, getters, symbols, Dates or class instances). Keys `__proto__`, `constructor` and `prototype` are dropped. Limits: 32 MB text, 2,000,000 values, depth 64, 100,000 resources, 2,000 characters per extracted string; control and bidi-override characters are removed. Resources with status `entered-in-error` or `cancelled` (or that verification status) are skipped and counted. Observations give value, unit, comparator, reference ranges, date (`effective[x]`, then `issued`), components (blood pressure) and `position` relative to the lab's own first reference range: `within`, `below`, `above`, or null when there is no numeric range or the units differ. Nothing else is interpreted. A few DSTU2 field names that Apple Health records still use are read as fallbacks (Immunization `date`, AllergyIntolerance `substance`, Condition `dateRecorded`).

**SMART Health Cards.** Accepts `shc:/` numeric QR text (each two digits are a character code minus 45; the deprecated multi-chunk form is refused), a compact JWS, or a `.smart-health-card` file. The payload is base64url decoded; if the header has `zip: "DEF"` it is passed to the caller's raw DEFLATE function (RFC 1951, no zlib header), then parsed with the same plain-JSON rules. The result carries `signature: "unverified"` and `verified: false`. This module never verifies signatures; the issuer is shown as claimed.

**ECG.** Apple Health `electrocardiograms/*.csv`: key-value header lines, then one microvolt sample per line. Kept: recorded date, classification, symptoms, software version, device, sample rate, lead. Name and date of birth are read past and not kept. Generic single-lead CSV: one value column with a stated or given sample rate, or time and value columns (seconds or ms; the rate is the median step); units in microvolts, millivolts or volts. Detector after Pan and Tompkins (1985): zero-phase 5 to 15 Hz band-pass (second-order Butterworth biquads, forward and backward, reflection padded), five-point derivative, squaring, 150 ms moving-window integration, signal and noise peak estimates updated at 0.125, threshold NPKI + 0.25 (SPKI - NPKI), 200 ms refractory period, 360 ms T-wave slope test, and search-back after 1.66 x the mean of the last 8 RR intervals. The search-back also accepts the largest missed peak when it stands above the noise estimate, which lets the threshold follow a sudden drop in QRS amplitude. Heart rate is from RR intervals between 0.25 and 3 s. Tested on synthetic signals (P, Q, R, S and T Gaussians, baseline wander, 60 Hz hum, noise) at 45 to 190 bpm, irregular rhythm, tall T waves, inverted polarity, 250 and 512 Hz, a premature beat and a 70 percent amplitude drop: every beat found within 25 ms (30 ms at 250 Hz) and no extra beats. It is not validated on clinical databases (MIT-BIH and similar are not used here). The device's classification is shown as the device's own text. Paper scale: 25 mm/s, 10 mm/mV.

**Clinician report.** Summaries per metric (n, mean, min, max, first-week and last-week mean, latest, weekly means with Monday weeks) for resting HR, RMSSD, SDNN, sleep, weight and blood pressure, plus labs and medications the user chose. Implausible values are skipped and counted. FHIR R4 Bundle of type `collection`: a Patient (name and birth date only if given), one Observation per day per metric, labs as `laboratory` Observations with the lab's range, and MedicationStatements. Codes: resting HR LOINC 40443-4 (`/min`), SDNN 80404-7 (`ms`), sleep duration 93832-4 (`h`), body weight 29463-7 (`kg`), blood pressure panel 85354-9 with systolic 8480-6 and diastolic 8462-4 (`mm[Hg]`), units in UCUM. RMSSD has no LOINC code that we could confirm, so it is sent as `code.text` only. HR, HRV, weight and BP use category `vital-signs`; sleep uses `activity`. The resources do not claim the FHIR vital-signs profile. `fullUrl`s are deterministic `urn:uuid` values hashed from the content, so the same input gives the same Bundle. The text summary lists numbers only, and a test checks it for diagnostic or advice words.

**AI coach.** The grounding pack is compact JSON: dates, a column list and rows for daily metrics (rounded, range-checked), activity rows (date, sport from a fixed list, duration, distance, load, average HR), 7-day and period means with counts, the readiness state, a list of metrics with no data, and units. Free text the user typed (activity names, notes) is never included, so a crafted name cannot carry instructions to the model. Oldest rows are dropped to fit `maxChars` (default 12,000). The system prompt tells the model to answer only from the DATA block, say when data is missing, quote dates and units, never give medical advice or name conditions or medicines, send symptoms to a clinician (or emergency services if severe), and reply in plain text. `checkQuestion` flags symptom words so the app can show the clinician notice itself. `guardOutput` decodes entities, removes script and similar elements, comments and any tag (repeated until stable), keeps markdown link labels, removes URLs (any scheme, `www.`, bare domains with common TLDs, IPv4), removes `<` and `>`, zero-width and control characters, and caps length. The app still renders replies with `textContent`. The guard is a filter, not a proof: a model can still say something wrong in plain words, which is why the pack is shown to the user.

**Calendar.** `sleepEvents` writes a VCALENDAR with two VEVENTs (bedtime, 15 minutes, with a display alarm; wake window, with a display alarm at its start), optional `RRULE:FREQ=DAILY`. Times are floating local times. Lines end in CRLF and are folded so no physical line exceeds 75 octets, never inside a UTF-8 sequence. TEXT values escape backslash, semicolon, comma and newline; colons are not escaped. Each event has UID and DTSTAMP (from the caller's `now`) and DTEND, never DURATION. A calendar event cannot wake anyone; the wake-window description says so.

## Verified against

Checked on 2026-10-21 with web fetches. Bitbucket (where the Bluetooth SIG now publishes YAML) was not reachable from the build machine, and the GATT Specification Supplement PDF was too large for the fetch tool to reach the relevant section, so the Bluetooth layouts were confirmed from the SIG's earlier XML definitions mirrored on GitHub plus the IEEE-11073 tables published by HL7 and Nordic.

- Bluetooth Heart Rate Measurement 0x2A37 field order, flag bits, sensor contact values 0 to 3, energy in kJ, RR in 1/1024 s: `org.bluetooth.characteristic.heart_rate_measurement.xml` (Bluetooth SIG XML, GitHub mirror oesmith/gatt-xml). Supplement location: https://www.bluetooth.com/specifications/gss/ (section 3.126 per its table of contents).
- Bluetooth Blood Pressure Measurement 0x2A35 field order, flag bits, measurement status bits and pulse rate range codes; Date Time layout and its "0 = unknown" year, month and day: `org.bluetooth.characteristic.blood_pressure_measurement.xml` and `org.bluetooth.characteristic.date_time.xml` (same mirror).
- SFLOAT layout (4-bit signed exponent, 12-bit signed mantissa) and special values 0x07FF, 0x0800, 0x07FE, 0x0802, 0x0801: HL7 Personal Health Device Implementation Guide, "FLOATs" page (https://www.hl7.org/fhir/uv/phd/en/FLOATS.html) and the Nordic nRF Connect SDK `sfloat.h` reference.
- FHIR R4 Observation elements (status, code, subject, effective[x], value[x], referenceRange low/high/text, component): https://hl7.org/fhir/R4/observation.html. Vital-signs LOINC codes and UCUM units (8867-4, 29463-7, 85354-9, 8480-6, 8462-4) and the `vital-signs` category: https://hl7.org/fhir/R4/observation-vitalsigns.html and https://hl7.org/fhir/R4/vitalsigns.html.
- LOINC 40443-4 "Heart rate --resting", 80404-7 "R-R interval.standard deviation (Heart rate variability)", 93832-4 "Sleep duration": loinc.org code pages.
- SMART Health Cards: `zip: "DEF"` raw DEFLATE with no zlib header, base64url, `shc:/` numeric encoding (character code minus 45), payload `iss`, `nbf`, `vc.type`, `vc.credentialSubject.fhirBundle`: https://spec.smarthealth.cards/.
- RFC 5545: 75-octet folding with CRLF plus one space and the UTF-8 warning (section 3.1, rfc-editor.org); TEXT escaping (3.3.11), VEVENT required UID and DTSTAMP and DTEND/DURATION exclusivity (3.6.1), DISPLAY alarm requires ACTION, DESCRIPTION and TRIGGER (3.6.6): icalendar.org section pages.
- Apple Health ECG export: 512 Hz, Lead I, microvolts confirmed from a public dataset description of Apple Watch ECG exports. The exact header line names are from common knowledge of the export format and are parsed leniently (unknown lines are ignored).

Not verified from a primary source: the FHIR R4 element names for Condition, MedicationStatement, MedicationRequest, Immunization and AllergyIntolerance were written from knowledge of R4 and checked only by tests against our own fixtures; Pan-Tompkins constants are from the 1985 paper as commonly reproduced, not re-read.
